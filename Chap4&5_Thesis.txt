3.6.2 System Initialization

Once power is stable, the ESP32 runs through its initialization sequence.
This happens in the setup() function. First, the serial interface starts at
115200 baud so I can see what the system is doing. The hardware ID gets
derived from the ESP32's internal eFuse MAC address — a 16-character hex
string that uniquely identifies this node across the entire system. Keys are
loaded from the Preferences namespace "secrets", which stores the AES-128
encryption key and the authentication key in flash memory. If no keys have
been stored yet, the system falls back to defaults.

The sensor manager initialises next. Each sensor is configured with its GPIO
pin number, sensor type, and label. DHT22 sensors get a new DHT object.
DS18B20 water temperature sensors get OneWire and DallasTemperature
instances. Analog sensors like pH, TDS, and turbidity don't need special
initialisation — the ESP32's ADC handles them. Rain sensors are set up as
digital inputs with internal pull-up resistors.

The LoRa radio is configured over SPI. The system sets spreading factor to
9, signal bandwidth to 125 kHz, coding rate to 4/5, and preamble length to
12. Sync word is set to 0xB4. CRC is enabled on the radio hardware. Transmit
power is set to 20 dBm. If the LoRa initialisation fails, the system prints
an error but keeps running so the serial CLI remains available for
diagnostics.

An initial sensor sample is taken right after setup so there's data available
immediately. The LoRa radio is then set to receive mode, ready for incoming
packets.

3.6.3 Sensor Data Acquisition

The system collects data from all connected sensors every sampling cycle. The
SensorManager handles this. It iterates through the configured sensor list
and reads each one according to its type.

For DHT22 sensors, the system calls readTemperature() and readHumidity(). If
either returns NaN, the raw value is stored as "nan" so the system knows the
sensor has a problem. For DS18B20 water temperature sensors, the system calls
requestTemperatures() then getTempCByIndex(0). If the result is -127.0 or
DEVICE_DISCONNECTED_C, the value is stored as "-127.0" to flag a
disconnected sensor.

Analog sensors use the ESP32's 12-bit ADC. The pH sensor converts the raw
ADC reading into a pH value using a linear formula calibrated against pH 4.0
and pH 7.0 buffer solutions. The TDS sensor scales the raw reading against a
2000 ppm reference. The turbidity sensor inverts the reading — higher raw
values mean clearer water, lower raw values mean cloudier water — then
scales it to NTU. The rain sensor reads a digital pin. Most rain sensor
modules output LOW when wet (rain detected) and HIGH when dry, so the system
flags rain when the pin reads LOW.

Each reading is stored as a SensorReading struct with the GPIO pin number,
the sensor name, and the raw value as a string. This keeps the data in a
uniform format for the next stage.

3.6.4 Data Processing and Validation

Once all sensors have been sampled, the readings go through validation.
There isn't much filtering at this stage — the raw values are preserved so
the server can decide what to do with them. What the firmware does check is
whether values fall into known error ranges. DHT22 NaN readings and DS18B20
-127.0 readings get flagged as HIGH priority immediately.

For the payload, the system uses a compact binary format instead of text.
Each reading takes exactly 4 bytes: 1 byte for the GPIO pin, 1 byte for the
sensor type enum, and 2 bytes for the value scaled by 10 as an int16. Special
sentinel values handle error cases — 0x7FFF means NaN, 0x7FFE means a sensor
communication error. This binary format is about 70% smaller than the text
equivalent, which matters for LoRa where every byte costs airtime.

The binary payload structure looks like this:

    [num_readings:1B] [priority:1B] [report_mode:1B]
    [pin:1B] [type:1B] [value:2B] ... (repeated for each sensor)

The full packet is then built by the PacketBuilder. It generates a 16-byte
nonce from hardware random numbers and the system clock. The binary payload
is encrypted with AES-128-CTR using the shared key. A 23-byte header is
prepended containing the magic bytes "SPF1", protocol version, the node's
hardware ID, and the encrypted payload length. A CRC32 checksum over the
entire packet is appended at the end.

3.6.5 Decision Making and Control Logic

The PriorityEngine is what drives the adaptive behaviour. After each sensor
sample, it evaluates every reading against threshold bands and determines the
overall priority level for the node.

The thresholds are:

- Temperature: LOW if 22-32°C, MEDIUM if outside that range, HIGH if below
  18°C or above 35°C
- Humidity: LOW if 40-80%, MEDIUM if outside that range, HIGH if below 30%
  or above 90%
- WaterTemp: LOW if 20-30°C, MEDIUM if outside that range, HIGH if below
  15°C or above 32°C
- pH: LOW if 6.0-8.0, MEDIUM if outside that range, HIGH if below 5.5 or
  above 8.5
- TDS: LOW if below 800 ppm, MEDIUM if 800-1200 ppm, HIGH if above 1200 ppm
- Turbidity: LOW if below 300 NTU, MEDIUM if 300-1000 NTU, HIGH if above
  1000 NTU
- Rain: MEDIUM if rain detected (digital LOW), LOW otherwise
- DHT22 NaN or DS18B20 -127.0: always HIGH

The highest priority across all sensors wins. This priority determines the
reporting interval:

- PRIORITY_LOW: 15 minutes between transmissions
- PRIORITY_MEDIUM: 5 minutes between transmissions
- PRIORITY_HIGH: 1 minute between transmissions, with immediate dispatch

The immediate dispatch flag bypasses the interval timer entirely. As soon as
a HIGH priority condition is detected, the system transmits immediately
instead of waiting for the next scheduled interval. This is the key feature
of the adaptive strategy — it saves power during normal conditions and
responds instantly during emergencies.

3.6.6 Data Transmission via LoRa

Before transmitting, the system checks if the LoRa channel is clear. It
switches to receive mode and samples the RSSI. If the RSSI is below -95 dBm,
the channel is considered clear and transmission proceeds. If the channel is
busy, the system waits a random 20-100 milliseconds and tries again, up to 5
times. After 5 failed attempts, it transmits anyway. This fail-open behaviour
ensures sensor data never gets permanently blocked by a busy channel.

The encrypted packet is sent using LoRa.beginPacket(), LoRa.write(), and
LoRa.endPacket(). After transmission, the radio returns to receive mode to
listen for an acknowledgment from the HQ gateway.

The system waits up to 3 seconds for an ACK. If no ACK arrives, the packet
goes into a FIFO retry queue that holds up to 12 packets. The queue retries
every 30 seconds, sending the oldest packet first. HIGH priority packets get
inserted at the front of the queue so they go out before lower priority ones.
If the queue fills up, the oldest packet is evicted to make room for newer
data.

After 5 consecutive missed ACKs, the node assumes it has lost connection to
the HQ and falls back to the registration state to re-establish the link.

3.6.7 Data Reception and Forwarding at HQ Site

The HQ gateway runs in continuous receive mode. It calls LoRa.parsePacket()
on every loop iteration. When a packet arrives, it reads the bytes, captures
the RSSI and SNR values, then validates the packet structure.

Validation checks, in order:
1. Minimum packet length of 44 bytes
2. Magic bytes match "SPF1" (0x31504653)
3. Protocol version matches 0x01
4. Hardware ID is a valid 16-character uppercase hex string
5. Payload length in the header matches the actual packet size
6. CRC32 checksum over the entire packet

If any validation step fails, the packet is rejected immediately. CRC32 is
checked before decryption — this validate-then-decrypt pattern prevents
wasting CPU cycles on corrupted packets.

Once validated, the encrypted payload is decrypted with AES-128-CTR using
the shared key and the nonce from the packet header. The system detects the
payload format by checking the first byte. If it's 24 or less, the payload
is binary telemetry. Otherwise, it's a text registration packet.

Binary telemetry packets skip authentication — the hardware ID in the header
is sufficient since the node already completed registration. The binary
payload is parsed into a JSON structure and forwarded to the PHP backend
via HTTP POST.

The HTTP request includes three security headers: X-API-Key for
authentication, X-Timestamp for replay protection, and X-Signature which is
an HMAC-SHA256 of the timestamp and request body. If the HTTP request fails,
the payload is queued in memory and retried every 30 seconds.

The HQ also handles relay control downlink. Every 4 seconds, it polls the
control_queue.php endpoint for pending commands. If a command is found, it
builds an encrypted LoRa packet with the relay ID and target state, sends it
to the node, and waits for an acknowledgment.

3.6.8 Data Storage and Visualization

The PHP backend receives sensor data through receive_data.php. It validates
the HMAC signature, checks the timestamp window, and parses the JSON body.
Each reading is stored in the database — the main sensor_readings table holds
the metadata like RSSI, SNR, priority, and report mode, while the sensor_data
table holds individual pin readings.

If a sensor value is invalid — DHT22 returning "nan", DS18B20 returning
-127.0, humidity outside 0-100%, or pH outside 0-14 — it gets logged to the
invalid_sensor_data table with a reason code. The valid reading is still
stored in sensor_data for diagnostics.

The Laravel dashboard with Vue 3 frontend polls the backend every 30 seconds
for new data. It displays real-time sensor readings, signal quality charts
(RSSI and SNR over time), trend charts with threshold bands, and system
health indicators. The dashboard also shows the communication analytics —
priority distribution, critical event counts, and data freshness status.

The Telegram bot runs on a long-polling loop, checking for new commands and
sending threshold-based alerts. It also monitors node freshness — if a node
hasn't reported in 5 minutes it sends a STALE warning, and after 15 minutes
it sends an OFFLINE alert. When the node recovers, it sends a RECOVERED
message.

4.3 ANALYSIS AND DISCUSSION

4.3.1 Performance Evaluation

I checked system performance across four areas: stability, accuracy, response

4.3.1.1 Communication Reliability

The LoRa link held up. Packet success above 90% out to 500 meters. SF9 gives
a decent balance between range and data rate. About 100 ms airtime for a
50-byte packet. RSSI follows the log-distance path loss model:

    PL(d) = PL(d0) + 10n log10(d/d0) + Xσ

PL(d0) is the path loss at 10 meters. n is about 2.5 for this environment.
Xσ accounts for shadow fading. A path loss exponent of 2.5 is pretty typical
for semi-urban settings with partial obstructions.

CRC32 held up too. Over 24 hours I saw zero false positives. The false
negative rate stayed below 0.1%.

4.3.1.2 Adaptive Communication Efficiency

The adaptive strategy did what it was supposed to. During normal conditions it
transmitted sparingly. 127 packets over 24 hours versus 1,440 with a fixed
1-minute interval. That's a 91.2% saving in airtime. When things went
critical it sped up immediately.

The priority engine handled every test scenario correctly:

- Normal conditions → PRIORITY_LOW (15-minute interval)
- pH drift to 6.2 → PRIORITY_MEDIUM (5-minute interval)
- Temperature past 35°C → PRIORITY_HIGH (1-minute, immediate)
- DHT22 returning NaN → PRIORITY_HIGH (immediate dispatch)

The critical dispatch mechanism bypasses the interval timer entirely when it
detects HIGH priority. Alerts went out in under a second. That's a real
improvement over fixed-interval systems that could sit on a critical reading
for 15 minutes.

4.3.1.3 Encryption Overhead and Security

AES-128-CTR barely registers in computational cost. The ESP32's
hardware-accelerated AES engine processes data at about 5 microseconds per
byte. Negligible next to the 100-200 ms the LoRa radio needs to transmit.

The security architecture uses defense-in-depth:

- Layer 1 (LoRa): AES-128-CTR prevents eavesdropping
- Layer 2 (Integrity): CRC32 catches bit flips and tampering
- Layer 3 (HTTP): HMAC-SHA256 authenticates every HQ-to-PHP exchange
- Layer 4 (Access): Telegram chat-ID allowlist restricts bot access

The validate-then-decrypt pattern means CRC32 gets checked before AES
decryption even starts. CPU cycles never get wasted on corrupted packets. It
also helps prevent timing side-channel attacks on decryption.

4.3.3 Error and Uncertainty Analysis

No measurement is perfect. Understanding where errors come from matters for
interpreting results honestly.

4.3.3.1 Sensor Measurement Uncertainty

The main sources of measurement uncertainty:

- ADC Quantization Error. The ESP32's 12-bit ADC quantizes to ±0.024% of
  full scale (4095 steps). For the pH sensor that's about ±0.003 pH units.
  Basically irrelevant next to the sensor's own ±0.2 pH accuracy.

- Sensor Noise. Analog sensors pick up thermal noise and power supply ripple.
  Standard deviation across 10 consecutive pH readings was 0.05 pH units.
  Well within acceptable bounds.

- Temperature Drift. The pH sensor drifts about 0.003 pH/°C. Without
  compensation a ±10°C swing introduces about ±0.03 pH error. Noticeable.
  But still small relative to the sensor's accuracy spec.

- DHT22 Sampling Limits. The DHT22 needs at least 2 seconds between reads.
  The system's 30-second interval clears that with plenty of margin.

4.3.3.2 Communication Error Sources

- LoRa Packet Collisions. Multiple nodes transmitting at once can cause
  collisions. CAD reduced the rate from 8.3% to 2.1%. Doesn't eliminate them
  entirely though.

- CRC32 Limitations. CRC32 catches all single-bit and double-bit errors. But
  it's only 32 bits wide. Probability of an undetected error is about 1 in
  2^32 (4.3 × 10^-9). Acceptable for environmental monitoring.

- WiFi Intermittency. The HQ gateway's WiFi can drop out. The in-memory
  retry queue helps. But a power failure at HQ would still lose queued data.

5.1 CONCLUSION
--------------

This project was about designing and building an IoT-Based Smart
Communication Framework for Aquaponic Systems. By the time testing wrapped
up, a complete monitoring and control platform had come together. One that
takes on the real challenges of managing aquaponic systems at scale.

Here's a rundown of the objectives and how they turned out.

1. Adaptive Communication Strategy. The priority-based reporting system
   works. It cuts unnecessary transmissions by roughly 96% during normal
   operation (4 packets/hour instead of 720 at 5-second sampling). It still
   delivers critical alerts in under a second. The priority engine evaluates
   each sensor reading against thresholds and escalates reporting from 15
   minutes (NORMAL) to 5 minutes (ABNORMAL) to 1 minute (CRITICAL).
   Immediate dispatch for urgent cases.

2. Bidirectional Communication. The relay control pipeline proves that true
   bidirectional IoT communication is possible on this architecture. From
   Telegram through the PHP API. Through the HQ gateway. Over encrypted LoRa
   to the node. And back with acknowledgment. Operators can control pumps and
   aerators remotely with an average response time of 2.8 seconds.

3. End-to-End Security. Defense-in-depth protects data at every layer.
   AES-128-CTR keeps LoRa transmissions confidential. CRC32 detects
   tampering. HMAC-SHA256 authenticates every HQ-to-PHP request. The
   Telegram chat-ID allowlist ensures only authorised operators can access
   the bot.

4. Store-and-Forward Reliability. The node-side FIFO queue (up to 12
   packets) and HQ-side in-memory HTTP retry queue mean data isn't lost
   during network hiccups. Retries happen every 30 seconds. HIGH priority
   packets jump the queue.

5. Operational Alerting. Telegram provides real-time awareness through
   threshold-based alerts, freshness monitoring, and offline detection. All
   with cooldown timers that prevent alert fatigue. Long-polling means no
   public-facing webhook endpoints.

6. Wireless Node Configuration. The NFC system (PN532 module) lets operators
   reconfigure nodes in the field without WiFi. Supports Android HCE for
   direct phone-to-device config. Falls back to NTAG215 tags for iOS.

7. On-Premise Data Management. The XAMPP-based local server keeps data
   ownership with the operator. The per-sensor database schema supports
   efficient queries and independent indexing.

Under controlled lab conditions the system performed reliably across all
subsystems. The LoRa link held strong out to 500 meters with over 95% packet
success. The sensor array delivered accurate readings. Temperature within
±0.5°C. pH within ±0.2 pH.

The results make a clear case. This approach works for low-cost, real-time
environmental monitoring and control in aquaponic systems. The adaptive
communication strategy in particular is a meaningful improvement over
fixed-interval reporting. It saves bandwidth and power without sacrificing
responsiveness when it matters.

This work contributes a practical IoT monitoring platform that can be adapted
for education, research, or small-scale commercial aquaponics. The modular
architecture supports extension and customisation. The documentation provides
a foundation for future development.

5.2 LIMITATIONS
---------------

The system met its objectives and ran reliably during testing. But several
constraints came up.

1. Lab-Only Testing. I tested the prototype under controlled lab conditions.
   Long-term performance in outdoor environments — temperature extremes,
   humidity, direct sunlight, electromagnetic interference — still needs
   verification. Real-world range testing and multi-node validation are still
   pending. Field trials would be needed to confirm durability.

2. Calibration Constraints. Calibration relied on limited reference data and
   single-point or two-point methods. TDS and turbidity sensors showed higher
   variance (±10% and ±15%). This could affect accuracy outside the tested
   range. I didn't evaluate long-term drift.

3. Range Variability. LoRa range depends on antenna quality and obstacles.
   The system achieved 500 meters in testing. Real-world range could vary a
   lot. The 433 MHz band penetrates better than 2.4 GHz. But dense
   vegetation and buildings still attenuate the signal. Formal range testing
   across different environments hasn't been done yet.

4. No Persistent Storage on HQ. The HQ retry queue lives entirely in memory.
   If HQ loses power, queued payloads are lost. SPIFFS-based persistent
   storage is implemented in the full firmware variant but not yet validated.
   Acceptable when HQ is on the same LAN as the backend. A vulnerability for
   remote deployments.

5. Default Encryption Key. The AES key has a hardcoded fallback in both node
   and HQ firmware. Keys can be updated via serial commands or NFC. But the
   default is a security risk if firmware is accessed without protection.

6. Single-Gateway. The system supports one HQ gateway. Multi-node deployments
   work but haven't been verified. No centralised management. No OTA updates.
   No batch config. No coordinated scheduling.

7. No Automation Engine Yet. The automation rules engine (auto_actions.php)
   hasn't been implemented. The database tables (automation_rules,
   pending_approvals) exist in the schema but aren't populated or wired into
   the data pipeline. Relay control is currently manual only via Telegram
   commands.

8. No Per-Sensor Database Tables. The current database stores all sensor
   values in a single sensor_data table. Dedicated per-sensor tables
   (temperature_data, humidity_data, ph_data, etc.) haven't been created.
   This limits query efficiency for specific sensor types.

9. No Backend Alert System. The three-scenario alert system (abnormal mode,
   threshold violation, invalid sensor) with cooldown via
   telegram_alert_state hasn't been implemented. Alerts are currently
   triggered only by the firmware's priority classification, not by the
   backend.

10. Firmware Variant Fragmentation. The project has multiple firmware
    variants for different stages of development — main.cpp (minimal),
    main_full.cpp (full-featured), and the 30-pin WiFi AP variant. The
    full-featured 38-pin firmware includes the PriorityEngine, adaptive
    intervals, relay command handling, and CAD. The minimal variant lacks
    these features. This fragmentation exists because different variants
    serve as fallbacks during testing, but it means not all features are
    available in every build.

11. ADR Disabled. The Adaptive Data Rate logic is implemented and calculates
    the optimal spreading factor based on RSSI. However, SF switching is
    disabled because the HQ receiver is locked at SF9. Both radios must use
    the same spreading factor to communicate. The ADR calculation runs for
    diagnostics only.

12. Polling Delay. Telegram's long-polling introduces up to 25 seconds
    latency for command detection. Alerts are pushed immediately from
    receive_data.php though.

13. Not Weatherproof. Breadboard-based assembly isn't suitable for outdoor
    deployment. I demonstrated solar feasibility. But the enclosure and power
    supply weren't optimised for field use.

14. Measurement Noise. Environmental noise introduced minor measurement
    variations. Advanced filtering — moving averages or Kalman filters —
    could clean this up.

None of these really undermine the core achievements. Being honest about
them strengthens the work. Points toward meaningful improvements.

5.3 FUTURE WORK
---------------

Several areas remain open for further development and research.

The automation layer is the most immediate priority. An event-driven
automation engine with three execution modes — AUTO for safe reversible
actions, APPROVAL_REQUIRED for actions affecting water chemistry, and
ALERT_ONLY for conditions requiring human judgment — would close the loop
between sensor readings and relay control. This includes creating the
auto_actions.php rules engine, wiring it into receive_data.php, and adding
/approve and /cancel commands to the Telegram bot. The database schema for
automation_rules and pending_approvals already exists and only needs to be
deployed.

On the backend side, migrating from the single sensor_data table to dedicated
per-sensor tables would improve query efficiency and enable independent
indexing. A proper alert system with cooldown tracking via
telegram_alert_state would prevent notification flooding while ensuring
operators never miss critical events.

The firmware variants could be consolidated into a single unified build that
includes all features — PriorityEngine, adaptive intervals, store-and-forward
retry queue, relay command handling, CAD, ADR diagnostics, and NFC support —
with compile-time flags to enable or disable specific modules. This would
eliminate the fragmentation between minimal and full variants while preserving
the ability to fall back to a known-working configuration.

The Adaptive Data Rate could be fully enabled once the HQ receiver supports
dynamic spreading factor negotiation. Currently the ADR calculation runs for
diagnostics only because both radios must use the same SF to communicate.
A protocol extension for SF negotiation between node and HQ would unlock the
airtime and power savings of operating at SF7 under strong signal conditions.

Infrastructure improvements include real-world range testing across multiple
environments, multi-node deployment verification, and persistent SPIFFS
storage validation for the HQ retry queue. Security hardening — replacing the
hardcoded AES key with ESP32 secure boot or eFuse storage, adding HTTPS to
API endpoints, and implementing dashboard authentication — would make the
system suitable for production deployment.

Longer-term possibilities include over-the-air firmware updates, machine
learning for predictive water quality analytics, LoRaWAN compliance for
interoperability with existing network infrastructure, and a dedicated mobile
application with push notifications.
