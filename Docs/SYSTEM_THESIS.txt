1.1 PROJECT BACKGROUND
----------------------

Aquaponics is a sustainable food production system that combines conventional
aquaculture (raising aquatic animals) with hydroponics (cultivating plants in
water) in a symbiotic environment. As aquaponics systems grow in complexity
and scale, manual monitoring becomes impractical. Real-time monitoring of
water quality parameters such as temperature, pH, dissolved oxygen, and
turbidity is essential to maintain optimal conditions for both fish and
plant health.

This project, SmartPonic, implements a complete IoT-based monitoring and
control system for aquaponics environments. The system employs ESP32
microcontrollers at each monitoring node, LoRa radio for long-range wireless
communication, a gateway hub connected to the internet, a PHP/MySQL backend,
Telegram for real-time alerts and remote control, and a web-based dashboard
for data visualization.

1.2 PROBLEM STATEMENT
----------------------

Traditional aquaponics monitoring systems face several challenges:

(a) Fixed reporting intervals waste bandwidth and power when conditions are
    normal, yet may be too slow to detect emergencies.

(b) Sensor failures (e.g., a DHT22 returning NaN) can go unnoticed for long
    periods, leading to data loss.

(c) Unencrypted LoRa radio transmissions are vulnerable to eavesdropping and
    replay attacks.

(d) One-way communication systems provide no way for operators to remotely
    control actuators such as water pumps or feeders.

(e) Cloud-dependent systems fail when internet connectivity is unavailable
    in remote farm locations.

1.3 PROJECT OBJECTIVES
----------------------

The primary objectives of this project are:

(i)   To implement an adaptive communication strategy that dynamically
      adjusts reporting intervals based on sensor conditions.

(ii)  To provide bidirectional communication enabling remote relay control
      via Telegram.

(iii) To secure all wireless transmissions using AES-CTR encryption with
      CRC32 integrity validation.

(iv)  To ensure data reliability through a store-and-forward architecture
      with offline buffering.

(v)   To deliver real-time alerts and system status through a Telegram bot.

(vi)  To provide a web-based dashboard for historical data analysis.

(vii) To enable wireless node configuration via NFC tap (Android HCE /
      NTAG215 physical tag).

(viii) To implement event-driven automation rules for automatic relay
      control based on sensor thresholds.

1.4 SCOPE AND LIMITATIONS
-------------------------

This implementation supports two ESP32 node variants:

ESP32 Node (30-pin variant):
- WiFi AP mode configuration (SSID: AQUA_NODE)

- Telegram as the sole notification and control channel

- CRC32 integrity validation
- Event-driven automation with human-in-the-loop approval for unsafe actions

Limitations:
- LoRa range is dependent on antenna quality and environmental obstacles
- SD card buffering on HQ requires hardware configuration (CS pin)
- The system uses a local XAMPP server rather than a cloud-hosted solution
- iOS uses physical NTAG215 tag workflow for NFC configuration (no direct HCE)

3.2 HARDWARE DEVICE IDENTITY (EUI-64)
--------------------------------------

Each ESP32 node carries a unique hardware identifier derived from its
internal eFuse MAC address. This EUI-64 (Extended Unique Identifier) is:

- Burned into ESP32 silicon at the Espressif factory
- Physically immutable (cannot be changed or cloned without special tools)
- Globally unique across all ESP32 devices ever manufactured
- Used as the definitive node identity in all system communications

The EUI-64 is derived from the 6-byte Bluetooth/WiFi MAC address:

    ESP32 MAC Address:  24:0A:C4:XX:XX:XX  (6 bytes, 12 hex chars)
    EUI-64 Format:     FFFEXXXXXXXXXX   (reversed + padded)

In SmartPonic, the EUI-64 is:
- Stored in ESP32 Preferences namespace "identity"
- Used as the primary key in the nodes database table
- Printed on the device label for physical identification
- Encoded in QR codes for rapid provisioning
- Carried in every LoRa packet header as the hardwareId field (16-char hex)

Persistence in Preferences:
The hardware device ID is stored at first boot and persists across firmware
reflashing (unless full flash erase is performed):

    Preferences prefs;
    prefs.begin("identity", false);        // namespace "identity"
    prefs.putString("eui64", euiString);   // e.g., "24A0C4FFFE112233"
    prefs.putString("device_name", "smartponic-node-1");
    prefs.end();

The hardwareId is placed directly in the LoRa packet header as a 16-byte
uppercase hex string, allowing HQ to identify the source node without
requiring any nodeId lookup table or runtime ID mapping.

3.4 PRIORITY CLASSIFICATION ENGINE
-----------------------------------

Each sensor reading is evaluated against threshold bands to determine its
priority level. The node takes the HIGHEST priority across all sensors.

+------------------+-------------------+-------------------+
| Sensor           | MEDIUM (ABNORMAL) | HIGH (CRITICAL)   |
+------------------+-------------------+-------------------+
| Temperature      | <22 or >32 C      | <18 or >35 C      |
| Humidity         | <40 or >80%       | <30 or >90%       |
| WaterTemp        | <20 or >30 C      | <15 or >32 C      |
| pH               | <6.0 or >8.0      | <5.5 or >8.5      |
| TDS              | >800 ppm          | >1200 ppm         |
| Turbidity        | >300 NTU          | >1000 NTU         |
| Rain (digital)   | Raining (1)       | ---               |
| DHT NaN reading  | ---               | Returns "nan"     |
| DS18B20 error    | ---               | Returns -127 C    |
+------------------+-------------------+-------------------+

The escalatePriority() function (line 213) returns the greater of two
priorities, ensuring the highest classification wins.

3.5 ADAPTIVE COMMUNICATION STRATEGY
-----------------------------------

This is the core innovation of the system. Instead of fixed reporting
intervals, the node dynamically adjusts based on conditions:

Reporting Intervals:
  PRIORITY_LOW    (NORMAL)    -> 15 minutes
  PRIORITY_MEDIUM (ABNORMAL)  -> 5 minutes
  PRIORITY_HIGH   (CRITICAL)  -> 1 minute

Additionally, CRITICAL conditions bypass the timer entirely and trigger
immediate transmission:

    void updateReportMode(uint8_t priority) {
        if (priority == PRIORITY_HIGH) {
            currentReportMode = REPORT_MODE_CRITICAL;
            currentReportIntervalMs = 60000UL;      // 1 minute
            criticalDispatchPending = true;          // <-- IMMEDIATE
        } else if (priority == PRIORITY_MEDIUM) {
            currentReportMode = REPORT_MODE_ABNORMAL;
            currentReportIntervalMs = 300000UL;      // 5 minutes
        } else {
            currentReportMode = REPORT_MODE_NORMAL;
            currentReportIntervalMs = 900000UL;      // 15 minutes
        }
    }

In the main loop, the sendCurrentTelemetry() function enforces this:

    if (currentPriority == PRIORITY_HIGH && criticalDispatchPending) {
        sendCurrentTelemetry(true);  // forceImmediate = true
    } else {
        sendCurrentTelemetry(false);
    }

The forceImmediate flag bypasses the interval check entirely.

This approach provides three key benefits:
1. Power efficiency: Normal conditions transmit only 4 times per hour
2. Responsiveness: Critical events are reported within 1 second
3. Bandwidth savings: No redundant transmissions during stable periods

3.6 STORE-AND-FORWARD RETRY QUEUE
---------------------------------

Failed LoRa transmissions are not silently dropped. The node maintains a
FIFO queue of up to 12 pending packets (MAX_PENDING_PACKETS):

    struct PendingPacket {
        std::vector<uint8_t> bytes;   // encrypted binary packet
        uint8_t priority;              // for queue ordering
        uint8_t reportMode;
        uint32_t sequence;
        unsigned long queuedAtMs;      // timestamp for aging
    };

Queueing behavior:
- HIGH priority packets are inserted at the front (highest priority first)
- LOW priority packets are appended to the back
- When the queue is full, the oldest packet is evicted (FIFO)
- Retry attempts occur every 30 seconds (RETRY_INTERVAL_MS)
- Only one packet is retried per interval to avoid flooding

4.2 BINARY PACKET STRUCTURE
---------------------------

The system uses a structured binary packet format (not ASCII HEX) to maximize
efficiency. Each packet consists of four sections:

+-----------+-----------+------------------+--------+
| HEADER    | NONCE     | ENCRYPTED        | CRC32  |
| 23 bytes  | 16 bytes  | PAYLOAD          | 4 bytes|
+-----------+-----------+------------------+--------+
|<-------- encrypted payload region ------>|
|<----------- full packet (variable) ----->|

HEADER (23 bytes, packed struct):
  Offset  Size  Field            Description
  ------  ----  -----            -----------
  0       4     magic            0x31504653 ("SPF1")
  4       1     version          Protocol version (1)
  5       16    hardwareId       EUI-64 MAC as 16-char uppercase hex string
  21      2     payloadLength    Encrypted payload size (little-endian)

The hardwareId field carries the node's full EUI-64 MAC address (e.g.,
"AC67B21234567890"), allowing HQ to identify the source node without
requiring a nodeId lookup table. This eliminates the need for a separate
registration step and simplifies the protocol.

NONCE (16 bytes):
  Offset  Size  Field            Source
  ------  ----  -----            ------
  0       4     random           esp_random() XOR
  4       4     timestamp        millis()
  8       4     random           esp_random()
  12      4     random           esp_random()

Each nonce is generated from three hardware random values and a millis()
timestamp, ensuring negligible probability of nonce reuse across the
key lifetime.

CRC32 (4 bytes):
  CRC32 checksum computed over HEADER + NONCE + ENCRYPTED_PAYLOAD.
  Validated BEFORE decryption to reject corrupted packets early.

4.2.1 Binary Payload Encoding

Telemetry data uses a compact binary encoding rather than text key-value
pairs. After decryption, the payload format is:

  [num_readings:1B] [pin:1B] [type:1B] [value:2B] ...

  Field            Size  Description
  -----            ----  -----------
  num_readings     1     Number of sensor readings (0-24)
  pin              1     GPIO pin number
  type             1     SensorType enum (0=Temperature, 1=Humidity,
                          2=WaterTemp, 3=pH, 4=TDS, 5=Turbidity, 6=Rain)
  value            2     int16_t scaled by 10 (25.3 -> 253)

  Special sentinel values:
    0x7FFF (BIN_VALUE_NAN)   - Sensor returned NaN (invalid reading)
    0x7FFE (BIN_VALUE_ERROR) - Sensor communication error

Each reading occupies exactly 4 bytes, enabling simple fixed-offset
parsing. A maximum of 24 readings per packet keeps the payload under
96 bytes, well within the LoRa maximum packet size.

4.2.2 Auth Key Optimization

The authentication key ("auth=AQUA77") is only included in registration
packets, not in routine telemetry. Since the packet header carries the
hardwareId, HQ can identify the node and look up its authentication
status without requiring an auth token in every transmission. This saves
8-10 bytes per telemetry packet, reducing airtime and power consumption.

4.3 ENCRYPTION (AES-CTR)
-------------------------

The system uses AES-128 in CTR (Counter) mode for authenticated encryption:

Why AES-CTR instead of AES-CBC?
- CTR mode does not require padding, eliminating padding oracle attacks
- Each packet uses a unique nonce, so identical plaintexts produce
  different ciphertexts (semantic security)
- CTR mode allows random access decryption (not needed here but a benefit)
- mbedTLS provides hardware-accelerated AES on ESP32

Encryption process:
1. Build binary payload: [count:1B][pin:1B][type:1B][value:2B]... for each sensor
2. Generate 16-byte nonce from (random XOR, millis, esp_random, esp_random)
3. Initialize AES-CTR with shared 128-bit key (same on all nodes/HQ)
4. Encrypt payload in one call -> encryptedPayload bytes
5. Assemble packet: [HEADER][NONCE][encryptedPayload][CRC32]

The nonce is transmitted in cleartext alongside the ciphertext. Since CTR
mode uses the nonce as a counter base (never reused within a key's lifetime),
transmitting it openly does not compromise security, provided no nonce is
ever reused. With 64 bits of (sequence + timestamp + random), the probability
of nonce collision is negligible.

4.4 CRC32 INTEGRITY VALIDATION
-------------------------------

CRC32 is computed BEFORE decryption (validate-then-decrypt pattern):

    checksum = CRC32(HEADER || NONCE || ENCRYPTED_PAYLOAD)
    packet   = HEADER || NONCE || ENCRYPTED_PAYLOAD || checksum

This ordering ensures:
- Corrupted packets are rejected before wasting CPU cycles on decryption
- Bit-flipping attacks on the encrypted payload are detectable
- The checksum itself is protected by being placed after the ciphertext

The CRC32 implementation uses the standard Ethernet polynomial (0xEDB88320)
with bit-reversed arithmetic, providing strong error detection capability.

4.5 CHANNEL ACTIVITY DETECTION (CAD)
-------------------------------------

Channel Activity Detection (CAD) is a listen-before-talk mechanism that
reduces packet collisions on the LoRa air interface. Before transmitting,
the node samples the channel RSSI to determine whether another transmission
is in progress.

Algorithm:
1. Switch to receive mode and sample RSSI
2. If RSSI < -95 dBm (channel clear), proceed with transmission
3. If RSSI >= -95 dBm (channel busy), wait a random 20-100 ms and retry
4. After 5 failed attempts, transmit anyway (fail-open behaviour)

The fail-open approach ensures that sensor data is never permanently
blocked by a persistently busy channel. In a typical deployment with
fewer than 10 nodes transmitting at multi-minute intervals, collisions
are rare and the CAD mechanism primarily prevents the rare case of two
nodes transmitting simultaneously after a shared event (e.g., power
restoration).

CAD is applied before both registration and telemetry transmissions,
and also before control command downlinks from HQ.

4.6 ADAPTIVE DATA RATE (ADR)
-----------------------------

Adaptive Data Rate (ADR) dynamically adjusts the LoRa spreading factor
(SF) based on the received signal strength (RSSI) of the HQ's ACK
response. Using a lower SF when signal conditions permit reduces airtime
and power consumption.

RSSI thresholds and corresponding spreading factors:

  RSSI Condition         Spreading Factor   Approximate Air Time (per 50B)
  ---------------        ----------------   ------------------------------
  RSSI > -100 dBm        SF7                 ~30 ms
  -110 < RSSI <= -100    SF8                 ~55 ms
  -120 < RSSI <= -110    SF9                 ~100 ms
  RSSI <= -120           SF10                ~185 ms

Algorithm:
1. After each telemetry transmission, capture the RSSI of the HQ's ACK
2. Track the best (highest) RSSI observed since the last ADR evaluation
3. Every 60 seconds, select the lowest SF that satisfies the RSSI threshold
4. Apply the new SF to subsequent transmissions via LoRa.setSpreadingFactor()

The ADR state is re-applied after light sleep, since the radio
configuration is reset on wake. This ensures the node always transmits
at the optimal SF regardless of sleep/wake cycles.

Benefits:
- Nodes with strong signal use SF7, reducing airtime by ~85% compared to SF10
- Reduced airtime lowers collision probability and power consumption
- Nodes with weak signal automatically fall back to higher SF for reliability
- No manual SF configuration required per node

5.1 LORA PACKET RECEPTION
-------------------------

The HQ gateway runs in continuous receive mode:

    void loop() {
        int packetSize = LoRa.parsePacket();
        if (packetSize) {
            // Read packet bytes
            std::vector<unsigned char> received(packetSize, 0);
            LoRa.readBytes(received.data(), packetSize);

            int rssi = LoRa.packetRssi();    // Signal strength
            float snr = LoRa.packetSnr();    // Signal-to-noise ratio
        }
    }

The RSSI and SNR values are captured and forwarded to the PHP API as signal
quality metrics, enabling the dashboard to track link health over time.

5.2 DECRYPTION AND VALIDATION
-----------------------------

HQ decrypts incoming packets using the shared AES-128-CTR key:

    processPacket()
    1. Verify minimum packet length (44 bytes)
    2. Verify magic bytes (0x31504653)
    3. Verify protocol version
    4. Extract hardwareId from header (offset 5, 16 bytes)
    5. Extract payload length from header (offset 21, 2 bytes LE)
    6. Verify total packet size matches expected size
    7. Verify CRC32 checksum (validate-then-decrypt)
    8. Extract nonce from packet
    9. AES-CTR decrypt with nonce
    10. Detect format: binary (telemetry) vs text (registration)

Format detection uses isBinaryFormat(): if the first byte of decrypted
payload is <= 24 (max readings count), it is treated as binary telemetry.
Otherwise it is treated as text (registration).

Binary telemetry packets skip auth validation — the hardwareId in the
packet header is sufficient for node identification. Text packets
(registration) are validated against the expected auth key.

5.3 HTTP FORWARDING WITH HMAC AUTHENTICATION
--------------------------------------------

HQ forwards validated sensor data to receive_data.php via HTTP POST:

    POST /smartponic/receive_data.php
    Headers:
        Content-Type: application/json
        X-API-Key: smartponic-hq-key
        X-Timestamp: 1714000000
        X-Signature: [HMAC-SHA256 of timestamp + body]

JSON payload format:
    {
      "hardware_id": "AC67B21234567890",
      "rssi": -45,
      "snr": 10.5,
      "event_type": "telemetry",
      "sensors": [
        {"pin": 32, "sensor": "pH", "value": "7.2"},
        {"pin": 33, "sensor": "TDS", "value": "450"}
      ]
    }

The HMAC-SHA256 signature ensures:
- authenticity: only HQ and PHP share the HMAC secret
- integrity: any body modification invalidates the signature
- replay protection: X-Timestamp prevents reuse of old requests

5.4 IN-MEMORY RETRY QUEUE
-------------------------

When HTTP POST fails (no WiFi or API unreachable), HQ queues payloads
in an in-memory vector for later retry:

    struct QueuedJob {
        String url;
        String body;
    };
    std::vector<QueuedJob> _queue;

Retry behavior (every 30 seconds, QUEUE_RETRY_MS):
    processQueue()
    1. Check WiFi connectivity; skip if disconnected
    2. Iterate through _queue vector
    3. Attempt httpPost() for each queued job
    4. On success: erase job from queue
    5. On failure: keep in queue, retry next cycle

The queue is purely in-memory — if HQ loses power, queued payloads
are lost. This is acceptable for the current deployment where HQ is
on the same LAN as the PHP backend and WiFi outages are rare.

5.5 RELAY CONTROL DOWNLINK
---------------------------

HQ also handles the downlink path for relay control commands:

    pollControlQueueIfNeeded()  // Every 4 seconds
    1. POST to control_queue.php with action=get_pending
    2. For each pending command:
       - Build encrypted LoRa control packet (cmd=relay, relay_id, state)
       - Send via LoRa to target node
       - POST to control_queue.php with action=mark_sent

When the node executes the relay command, it sends an encrypted ACK back
via LoRa. HQ receives this ACK and forwards it:

    handleControlAckIfPresent()
    1. Detect ack=relay in decrypted payload
    2. Extract command_id, status, message
    3. POST to control_queue.php with action=ack

6.1 API ENDPOINT (receive_data.php)
-----------------------------------

This is the primary ingestion point for all sensor data. Its responsibilities:

1. Validate signed HTTP requests (API key + HMAC + timestamp)
2. Parse and validate incoming JSON
3. Route sensor values to per-sensor tables
4. Trigger Telegram alerts
5. Apply data retention policies

Request validation flow:
    verifySignedRequest(rawJson)
    1. Check X-API-Key matches SMARTPONIC_API_KEY
    2. Check X-Timestamp is numeric and within 5 minutes of server time
    3. Compute HMAC-SHA256(timestamp + "\n" + body)
    4. Compare against X-Signature (constant-time comparison via hash_equals)

Input validation:
- hardware_id: must be a valid 16-char uppercase hex string
- sensors: must be non-empty array, max 32 items
- Each sensor: must have pin (int), sensor (string), value (string)

6.2 DATA ROUTING TO PER-SENSOR TABLES
--------------------------------------

Instead of storing all sensor values in one generic table, the system uses
dedicated tables for each sensor type:

    sensor_readings (main record)
        |
        +-- temperature_data (reading_id, node_id, pin, value)
        +-- humidity_data
        +-- water_temp_data
        +-- ph_data
        +-- tds_data
        +-- turbidity_data

This design enables:

Invalid sensor values are logged to invalid_sensor_data:

- DS18B20 returning -127 -> reason: "Check DS18B20 sensor"

6.3 CONTROL QUEUE ENDPOINT (control_queue.php)
----------------------------------------------

This endpoint manages relay command state machine:

    States: pending -> sent -> done | failed

Actions:
    get_pending(node_id, limit, mark_sent)
        - Returns pending commands for a node
        - Optionally marks them as "sent" (so they aren't re-queued)

    mark_sent(command_id)
        - HQ calls after successfully transmitting via LoRa

    ack(command_id, status, message)
        - HQ calls after receiving ACK from node
        - status: "done" or "failed"
        - Updates done_at timestamp and result_message

                       CHAPTER 7: TELEGRAM INTEGRATION

7.1 BOT ARCHITECTURE (LONG POLLING)
-----------------------------------

Instead of webhook-based callbacks (which require a public-facing server),
the system uses a long-polling runner (telegram_poll.php):

    Run modes:
    php telegram_poll.php --once   -> Process one batch, then exit
    php telegram_poll.php --loop   -> Continuous polling (for systemd/service)

Polling mechanism:
    offset = telegramGetLastUpdateId()
    updates = telegramGetUpdates(offset + 1, timeout=25)
    for each update:
        parse command
        execute handler
        telegramSetLastUpdateId(update_id)

The offset mechanism ensures no update is processed twice, even across
process restarts. State is persisted in MySQL tables.

7.2 ALERT SYSTEM
----------------

Telegram alerts are triggered from receive_data.php in three scenarios:

Scenario 1: Firmware report mode is ABNORMAL or CRITICAL
    - Triggered by: receive_data.php (lines 366-428)
    - Cooldown: 300 seconds (CRITICAL), configurable
    - State key: "node:{id}:mode:{mode}"

Scenario 2: Dashboard threshold profile violation (even during NORMAL)
    - Triggered by: receive_data.php (lines 434-524)
    - Uses per-sensor threshold_min/threshold_max from sensor_profiles
    - Cooldown: cooldown_abnormal_s (default 300s)
    - State key: "node:{id}:threshold:{sensor}:{low|high}"

Scenario 3: Invalid sensor readings
    - Triggered when: invalid_sensor_data has entries for this reading
    - State key: "node:{id}:invalid_sensors"
    - Cooldown: 300 seconds

Alert cooldown prevents flood attacks on Telegram:
    telegramShouldSendAlert(stateKey, cooldownSeconds)
    1. Query last_sent_at for stateKey
    2. If never sent OR (now - last_sent_at) >= cooldownSeconds -> ALLOW
    3. Otherwise -> SUPPRESS

7.3 BIDIRECTIONAL COMMANDS
--------------------------

Available Telegram commands:

/whoami              - Returns the user's chat ID (for allowlist setup)
/help, /start        - Shows all available commands
/status [node]       - Latest packet summary (priority, mode, RSSI, alerts)
/readings [node]     - Latest sensor values with units
/alerts [node]       - List of alerts (active/ack/resolved)
/ack <node> <key>   - Acknowledge an active alert
/resolve <node> <key> - Mark an alert as resolved
/relay <node> <id> <on|off> - Queue a relay command for execution
/queue [node]        - View pending relay commands

Example relay flow:
    User: /relay 1 0 on
    Bot:  Queued relay command #42: node 1 relay 0 ON
    HQ:   (polls, gets pending command)
    HQ:   (sends encrypted LoRa packet to node)
    Node: (executes GPIO toggle, sends ACK)
    HQ:   (receives ACK, posts to control_queue.php)
    Bot:  (no direct reply; user sees /queue cleared)

7.4 COOLDOWN AND DEDUPLICATION
------------------------------

The alert state table (telegram_alert_state) stores the last_sent_at
timestamp for each unique alert state key:

    CREATE TABLE telegram_alert_state (
        state_key VARCHAR(190) PRIMARY KEY,
        last_sent_at TIMESTAMP NULL,
        updated_at TIMESTAMP
    );

This is shared between receive_data.php (alert sending) and telegram_poll.php
(freshness checking), ensuring coherent cooldown across both entry points.

For database resilience, if InnoDB tables fail (XAMPP tablespace issues),
the system automatically falls back to MyISAM variants:
    telegram_bot_state_v2 + telegram_alert_state_v2 (MyISAM)

7.5 FRESHNESS MONITORING
------------------------

The telegram_poll.php --loop process also monitors node health:

    telegramFreshnessCheck()
    1. For each registered node:
       - Get last sensor_readings.created_at
       - age = now - created_at
       - If age >= freshness_offline_s:
            send "SmartPonic OFFLINE" alert (cooldown: 300s)
         If age >= freshness_warning_s:
            send "SmartPonic STALE" alert (cooldown: 300s)
         If OFFLINE was sent but node recovered:
            send "SmartPonic RECOVERED" message

This provides a watchdog mechanism: if a node stops transmitting for
too long (configurable, e.g., 5 minutes for STALE warning, 15 minutes for
OFFLINE alert), operators receive a Telegram notification even without
explicit CRITICAL detection.

================================================================================
                         CHAPTER 9: SECURITY ARCHITECTURE
================================================================================

9.1 LORA LAYER SECURITY (AES-CTR)
---------------------------------

All LoRa payloads are encrypted with AES-128-CTR using a shared 128-bit
key ("SmartPonic123456"). This provides:

- Confidentiality: Eavesdroppers cannot read sensor data
- Semantic security: Identical plaintexts produce different ciphertexts
  (due to unique nonce per packet)
- No padding oracle attacks: CTR mode does not use padding

Key management consideration:
The symmetric key is hardcoded in both node and HQ firmware. In production,
this should be stored in ESP32 secure boot eFuses or an encrypted flash
partition. The current implementation assumes a trusted deployment environment.

9.2 INTEGRITY PROTECTION (CRC32)
---------------------------------

CRC32 checksum is appended to every packet and validated at HQ before
decryption:

    receivedChecksum = packet[packetSize - 4 ... packetSize - 1]
    calculatedChecksum = CRC32(packet[0 ... packetSize - 5])

This prevents:
- Bit flip errors during LoRa transmission
- Malformed packet injection attacks
- Truncated or garbled packet acceptance

The checksum covers the encrypted region, protecting both plaintext
content and structural fields from tampering.

9.3 HTTP API SECURITY (HMAC-SHA256)
------------------------------------

Every HTTP request from HQ to PHP includes three security headers:

    X-API-Key:       Shared API key (pre-shared between HQ and PHP)
    X-Timestamp:     Unix timestamp of request generation
    X-Signature:     HMAC-SHA256(timestamp + "\n" + body, secret)

PHP validates:
1. API key matches (authenticates the caller)
2. Timestamp is recent (within 5 minutes, prevents replay)
3. HMAC signature matches (ensures body integrity)

Replay attack prevention:
The 5-minute timestamp window (SMARTPONIC_REQUEST_MAX_AGE_SECONDS) ensures
captured requests cannot be replayed after 5 minutes. The HMAC prevents
modification of the body within that window.

9.4 NODE CONFIGURATION PROTECTION
-----------------------------------

Node firmware endpoints are protected by X-Node-Key:

    requireAuthorizedNodeKey(allowBootstrap)
    - If no key configured: allow deployment (bootstrap mode)
    - If key configured: require matching X-Node-Key header
    - Invalid key -> HTTP 403

This prevents unauthorized reconfiguration of sensor pins, calibration
coefficients, or node identity after initial deployment.

9.5 TELEGRAM ACCESS CONTROL
----------------------------

Telegram bot access is restricted to an allowlist of chat IDs:

    telegramIsAllowedChat(config, chatId)
    1. Load allowed_chat_ids from telegram_config.php
    2. Compare incoming chatId against allowlist
    3. Reject with "Unauthorized chat" message if not found

This ensures that even if someone discovers the bot's username, they
cannot issue commands or receive alerts without explicit authorization.

================================================================================
                    CHAPTER 10: NFC CONFIGURATION SYSTEM
================================================================================

10.1 NFC CONFIGURATION OVERVIEW
-------------------------------

SmartPonic supports wireless node configuration via NFC tap. Instead of
connecting the ESP32 Node to a WiFi access point for HTTP-based
configuration, users can tap their phone directly to the PN532 NFC module
attached to the ESP32. This is particularly useful for:

- Quick reconfiguration in the field without opening the enclosure
- Scenarios where WiFi infrastructure is unavailable
- iOS users who cannot use Android HCE (Host Card Emulation)
- Physical audit trail via NFC tag interchange

The system implements two complementary NFC paths:

(a) Direct Android HCE (Host Card Emulation): Primary method for Android
    users. The phone emulates an NFC smart card; ESP32 reads config
    directly from the phone via ISO-DEP protocol.

(b) Physical NTAG215 Tag: iOS fallback. The Flutter app writes an
    encrypted config to a physical NTAG215 NFC tag; the user then taps
    the tag to the ESP32 PN532 reader.

10.2 PN532 HARDWARE INTERFACE
-----------------------------

The PN532 NFC module is connected to the ESP32 Node via I2C:

    PN532 Pin    ESP32 GPIO
    ---------   ----------
    VCC         5V
    GND         GND
    SDA         GPIO 21 (I2C SDA)
    SCL         GPIO 22 (I2C SCL)
    IRQ         GPIO 27 (interrupt, optional)
    NSS         GND (I2C mode select)

The PN532 is initialized over I2C using the Adafruit_PN532 library:

    Wire.begin(NFC_I2C_SDA, NFC_I2C_SCL);  // Start I2C bus
    _nfc.begin();                          // Initialize PN532
    _nfc.setPassiveActivationRetries(0xFF);
    _nfc.SAMConfig();                      // Configure Secure Access Module

LED indicator on GPIO 2 provides visual feedback:
- Solid ON while waiting for NFC tap
- Flashing during read operation
- 5 quick flashes on successful configuration

10.3 DIRECT ANDROID HCE (HOST CARD EMULATION)
--------------------------------------------

When an Android phone running the SmartPonic app taps the PN532:

    [Android Phone]  ---ISO-DEP APDU---  [PN532]  ---I2C---  [ESP32 Node]

The phone's HCE service registers with the Android OS an AID (Application
Identifier): F0.53.4D.41.52.54.50.4F.4E.49.43 (ASCII: "F0.SMARTPONI C")

The ESP32 acts as the NFC reader, sending APDU commands and collecting
responses from the phone. The protocol sequence is:

Step 1 - Target Selection:
    The ESP32 polls for ISO14443A targets using inListPassiveTarget().
    On detection, it selects the SmartPonic AID.

Step 2 - SELECT AID APDU:
    Command:  00 A4 04 00 0B F0 53 4D 41 52 54 50 4F 4E 49 43 00
    Response: 90 00 (status: success, SW1-SW2)

Step 3 - GET LENGTH APDU:
    Command:  00 CA 00 00 04
    Response: [4-byte big-endian payload length] + 90 00
    The 4-byte length indicates total encrypted payload size (max 2048).

Step 4 - READ BINARY APDU (chunked):
    Command:  00 B0 [offset_hi] [offset_lo] [max_len]
    Response: [data chunk] + 90 00
    Payload is read in 48-byte chunks until full length is retrieved.

Step 5 - AES-CTR Decryption:
    Once complete encrypted payload is received:
    [16-byte IV/nonce] + [ciphertext] -> AES-CTR decrypt -> JSON config

The ESP32 implementation (NFCConfigReader::readDirectHceConfig):

    exchangeApdu() wraps inDataExchange() for APDU send/receive
    isSuccessStatus() checks response SW (90 00 = OK)
    decryptPayload() performs AES-CTR with the node's stored AES key

10.4 PHYSICAL NTAG215 TAG FALLBACK
----------------------------------

For devices without HCE support (iOS), or as a backup method:

    [Android Phone]  ---NFC write---  [NTAG215 Tag]  ---NFC read---  [ESP32]

The NTAG215 NFC tag has 135 pages of 4 bytes each (540 bytes total user
memory, 504 bytes usable for application data):

    Pages 0-3:   Manufacturer data (read-only, locked)
    Pages 4-39:  Primary user memory (144 bytes)
    Pages 40-135: Extended user memory (384 bytes)

The ESP32 reads pages starting at page 4:

    page = 4
    while offset < NFC_MAX_PAYLOAD_SIZE:
        ntag2xx_ReadPage(page, pageData)  // 4 bytes per page
        Copy pageData to buffer
        page++
        if page > 135: break

The raw data is parsed as an NDEF (NFC Data Exchange Format) record:

    [Header (1B)] [Type Len (1B)] [Payload Len (4B, BE)] [Type] [Payload]
    -> Extract payload (encrypted config)

The encrypted payload is then AES-CTR decrypted using the same key.

Note: Physical tag storage is limited to ~500 bytes. For large
calibration profiles or extended sensor configurations, the Android
HCE path is preferred (no memory limit).

10.5 ENCRYPTION AND SECURITY
----------------------------

All NFC payloads use AES-128-CTR encryption, identical to the LoRa
communication layer:

    Key:         16-character string from ESP32 Preferences "secrets" namespace
    Nonce/IV:    16 bytes prepended to ciphertext
    Mode:        AES-128-CTR (same function for encrypt/decrypt)
    Plaintext:   JSON config: { config, nodeId, lat, lon, calibration, keys, seq, ts }

The AES key is shared between:
- LoRa transmitter (node -> HQ)
- NFC configuration (phone -> node)

Note: The HTTP API uses a separate HMAC-SHA256 authentication scheme
with its own secret key, not the AES encryption key.

This means the Flutter app must use the same AES key to encrypt the NFC
payload as configured in the ESP32 node's flash storage.

Security notes:
- No per-packet authentication (HMAC) on NFC payloads
- Replay protection via seq (sequence number) and ts (timestamp) in JSON
- Physical access required for NFC configuration (tap phone to device)
- Optional: node_key header can enforce additional configuration protection

10.6 IOS FALLBACK WORKFLOW
--------------------------

iOS does not support third-party HCE (Host Card Emulation). Apple
restricts NFC card emulation to Apple Pay and specific use cases.

iOS users configure the ESP32 Node via physical NFC tag:

    1. User configures ESP32 settings in SmartPonic Flutter app
    2. User taps phone to blank NTAG215 NFC tag
    3. Flutter app encrypts config and writes to NTAG215 pages
    4. User physically presents tag to ESP32 PN532 reader
    5. ESP32 reads, decrypts, and applies configuration
    6. Confirmation via LED flash pattern on ESP32

The same ESP32 NFCConfigReader class handles both workflows:
- HCE path: attempts first (inListPassiveTarget + ISO-DEP APDUs)
- NTAG215 path: automatic fallback if HCE read fails

                CHAPTER 11: EVENT-DRIVEN AUTOMATION
================================================================================

11.1 AUTOMATION ARCHITECTURE
-----------------------------

SmartPonic implements an event-driven automation layer that evaluates
sensor readings against configurable threshold rules and executes
corresponding relay actions. The automation system is designed with a
human-in-the-loop safety model: safe actions execute automatically,
while unsafe actions require explicit Telegram approval before execution.

The automation engine is triggered in receive_data.php after each
validated sensor reading is stored:

    evaluateAutomationRules(nodeId, sensorKey, value, priority)
    1. Load active automation rules for this node + sensor
    2. Evaluate condition (threshold comparison)
    3. If condition met:
       - AUTO mode:        create relay command immediately + notify Telegram
       - APPROVAL mode:    create pending_approval + send approval request
       - ALERT_ONLY mode:  send Telegram alert only

Automation failures (database errors, Telegram send failures) must never
break the data ingestion pipeline. All automation logic is wrapped in
try-catch with silent failure logging.

11.2 AUTOMATION RULES TABLE
---------------------------

Each automation rule defines a single sensor-threshold-action mapping:

    CREATE TABLE automation_rules (
      id                INT AUTO_INCREMENT PRIMARY KEY,
      node_id           TINYINT UNSIGNED NOT NULL,
      sensor_key        VARCHAR(32) NOT NULL,        -- e.g., "turbidity", "ph"
      condition_type    ENUM('high','low') NOT NULL,
      threshold_value   DECIMAL(10,4) NOT NULL,
      target_relay_id   TINYINT UNSIGNED NOT NULL,    -- GPIO index on node
      target_action     ENUM('ON','OFF') NOT NULL,
      execution_mode    ENUM('auto','approval_required','alert_only') NOT NULL,
      active            BOOLEAN DEFAULT TRUE,
      cooldown_seconds  INT UNSIGNED DEFAULT 300,
      created_at        TIMESTAMP DEFAULT CURRENT_TIMESTAMP
    );

Default aquaponics automation rules (seeded at system setup):

    | Sensor      | Condition | Threshold  | Relay | Action | Mode            |
    |-------------|-----------|------------|-------|--------|-----------------|
    | turbidity   | > 300 NTU | 300        | 0     | ON     | AUTO            |
    | turbidity   | < 250 NTU | 250        | 0     | OFF    | AUTO            |
    | water_temp  | > 30 C    | 30         | 0     | ON     | AUTO            |
    | water_temp  | < 18 C    | 18         | 0     | ON     | ALERT_ONLY      |
    | ph          | < 6.0     | 6.0        | 1     | ON     | APPROVAL        |
    | ph          | > 8.0     | 8.0        | 1     | ON     | APPROVAL        |
    | tds         | > 800     | 800        | 1     | ON     | ALERT_ONLY      |
    | temperature | > 35 C    | 35         | 1     | ON     | ALERT_ONLY      |

Each rule has an independent cooldown to prevent rapid flapping.
The cooldown is tracked per-rule, keyed as: "node:{id}:rule:{ruleId}"

11.3 EXECUTION MODES
--------------------

SmartPonic defines three execution modes that reflect the severity and
reversibility of the action:

AUTO (automatic execution):
    The relay command is created immediately without waiting.
    Telegram notification is sent concurrently.
    Appropriate for: safe, reversible actions (water circulation via pump).

    Flow: threshold crossed -> create relay_command (status=pending) ->
           send Telegram notification -> HQ polls -> forwards to node

APPROVAL_REQUIRED (human-in-the-loop):
    A pending approval record is created, blocking relay execution.
    A Telegram request is sent to the operator asking for /approve {cmdId}.
    If not approved within 10 minutes, the pending command expires.

    Flow: threshold crossed -> create pending_approval ->
           send Telegram approval request -> wait for /approve or /cancel
           -> on approve: execute relay_command -> on cancel: discard

ALERT_ONLY (monitoring only):
    No relay action is taken. A Telegram alert is sent to alert the
    operator, who must take manual action.

    Flow: threshold crossed -> send Telegram alert only

11.4 PENDING APPROVALS WORKFLOW
------------------------------

When an APPROVAL_REQUIRED rule triggers:

    CREATE TABLE pending_approvals (
      id           INT AUTO_INCREMENT PRIMARY KEY,
      command_id   INT UNSIGNED NOT NULL,        -- FK to relay_commands.id
      rule_id      INT NOT NULL,
      node_id      TINYINT UNSIGNED NOT NULL,
      relay_id     TINYINT UNSIGNED NOT NULL,
      action       VARCHAR(4) NOT NULL,
      trigger_value DECIMAL(10,4) NOT NULL,
      status       ENUM('pending','approved','cancelled','expired') DEFAULT 'pending',
      chat_id      BIGINT,
      created_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
      expires_at   TIMESTAMP DEFAULT (CURRENT_TIMESTAMP + INTERVAL 10 MINUTE)
    );

The 10-minute expiration prevents stale commands from executing if the
operator is unavailable. If no /approve or /cancel is received within
10 minutes, the command transitions to 'expired' and is cleaned up.

Expire check runs during each telegram_poll.php cycle:
    expirePendingApprovals()
    1. UPDATE pending_approvals SET status='expired'
       WHERE status='pending' AND expires_at < NOW()
    2. DELETE expired records older than 24 hours

11.5 TELEGRAM /approve AND /cancel COMMANDS
-------------------------------------------

Operator approves a pending automation command:

    User: /approve 42
    Bot:  Approving automation command #42 (node 1 relay 0 ON)
    Bot:  Command executed. Node confirmed: pump ON.

    Command execution:
    1. Validate user chat_id is in allowed_chat_ids
    2. Verify pending_approvals.id = 42 AND status = 'pending'
    3. Update status = 'approved'
    4. Create or update relay_commands record with target relay state
    5. HQ polls, forwards to node, receives ACK

Operator cancels a pending automation command:

    User: /cancel 42
    Bot:  Cancelled automation command #42 (node 1 relay 0 ON)

    Cancellation:
    1. Validate chat_id
    2. Update pending_approvals.status = 'cancelled'
    3. relay_commands record is left as-is (already expired if not acted on)

11.6 SAFETY PRINCIPLES
----------------------

The automation system is designed with multiple layers of safety:

1. SAFE ACTIONS ONLY: AUTO mode is only used for physically reversible
   actions (water pump toggle for circulation/filtration). It is never
   used for chemical dosing (pH adjusters) or temperature control.

2. APPROVAL FOR HAZARDOUS ACTIONS: Any action affecting water chemistry
   (pH dosing, nutrient dosing) is APPROVAL_REQUIRED. This ensures a
   human operator assesses the situation before any chemical is introduced.

3. ALERT_ONLY FOR UNCERTAIN: When the correct response is ambiguous
   (water temperature too low - heating is complex/dangerous), the
   system alerts the operator without attempting any automatic response.

4. INDEPENDENT COOLDOWNS: Each automation rule has its own cooldown
   timer. A triggered rule does not affect cooldown timers on other rules.

5. HARDWARE INTERLOCK: Physical relay wiring should include normally-open
   contacts and manual overrides, ensuring manual shutdown is always
   possible regardless of firmware state.

6. EXPIRY ON PENDING: Pending approvals expire after 10 minutes if
   unacted upon, preventing stale commands from executing.
