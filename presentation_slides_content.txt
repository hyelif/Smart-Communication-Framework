================================================================================
  SLIDE 2 — ABSTRACT / PROJECT OVERVIEW
================================================================================

Title:
  Abstract — Project Overview

Content:

  SmartPonic is a complete IoT-based monitoring and control system designed
  for aquaponics environments — a sustainable food production system combining
  aquaculture (fish farming) with hydroponics (soilless plant cultivation).

  Key Capabilities:
  • Real-time monitoring of water quality parameters:
    - Temperature, pH, TDS (Total Dissolved Solids), Turbidity
    - Air temperature & humidity (DHT22)
    - Water temperature (DS18B20)
    - Rain detection

  • Long-range wireless communication via LoRa (433 MHz)
    - AES-128-CTR encrypted transmissions
    - Adaptive Data Rate (SF7–SF10) based on signal strength
    - Binary payload encoding (~70% size reduction)

  • Bidirectional control pipeline:
    - Telegram → PHP API → ESP32 HQ Gateway → LoRa → ESP32 Node
    - Remote relay control for water pumps and actuators

  • Event-driven automation with human-in-the-loop safety:
    - AUTO mode for safe, reversible actions
    - APPROVAL_REQUIRED for chemistry-affecting actions
    - ALERT_ONLY for monitoring without automatic action

  • Multi-channel alerting:
    - Telegram bot with real-time alerts
    - Freshness monitoring (STALE / OFFLINE / RECOVERED)
    - Web dashboard with predictive analytics

  • NFC configuration (38-pin node variant):
    - Android HCE direct phone tap
    - NTAG215 physical tag fallback (iOS)

================================================================================
  SLIDE 3 — INTRODUCTION & PROBLEM STATEMENT
================================================================================

Title:
  Introduction & Problem Statement

Content:

  Background:
  • Aquaponics combines fish farming and hydroponics in a symbiotic ecosystem
  • Fish waste provides nutrients for plants; plants filter water for fish
  • Water quality is critical — small changes can kill fish or damage crops
  • Manual monitoring is impractical at scale

  Problem Statement — Five Key Challenges:

  1. FIXED REPORTING INTERVALS
     - Waste bandwidth and power when conditions are normal
     - Too slow to detect emergencies when they occur
     - No dynamic adjustment based on sensor readings

  2. UNDETECTED SENSOR FAILURES
     - DHT22 returning NaN can go unnoticed for long periods
     - Leads to data loss and delayed response

  3. UNSECURED WIRELESS COMMUNICATION
     - Unencrypted LoRa transmissions vulnerable to eavesdropping
     - Replay attacks possible without integrity protection
     - No authentication mechanism for data origin

  4. ONE-WAY COMMUNICATION
     - No way to remotely control actuators (pumps, feeders)
     - Operator must be physically present to respond to alerts

  5. CLOUD DEPENDENCY
     - Cloud-dependent systems fail without internet connectivity
     - Remote farm locations often have unreliable internet

  NODE FIRMWARE ARCHITECTURE:

  State Machine:
    STATE_REGISTERING ──(registration accepted)──► STATE_CONNECTED
         │                                                  │
         │ 30s retry                                        │ 90s sampling cycle
         ▼                                                  ▼
    Send registration packet                          Sample sensors
    Wait for approval                                  Classify priority
                                                       Build binary payload
                                                       CAD check → Transmit
                                                       Wait for ACK (3s)
                                                       Light sleep

  Priority Classification Engine:
  ┌──────────────┬──────────────────┬──────────────────┐
  │ Sensor       │ MEDIUM (Abnormal)│ HIGH (Critical)  │
  ├──────────────┼──────────────────┼──────────────────┤
  │ Temperature  │ <22 or >32°C    │ <18 or >35°C     │
  │ Humidity     │ <40 or >80%      │ <30 or >90%      │
  │ WaterTemp    │ <20 or >30°C     │ <15 or >32°C     │
  │ pH           │ <6.0 or >8.0     │ <5.5 or >8.5     │
  │ TDS          │ >800 ppm         │ >1200 ppm        │
  │ Turbidity    │ >300 NTU         │ >1000 NTU        │
  │ Rain         │ Raining (1)      │ —                │
  │ DHT NaN      │ —                │ Returns "nan"    │
  │ DS18B20 err  │ —                │ Returns -127°C   │
  └──────────────┴──────────────────┴──────────────────┘

  Adaptive Communication:
  • PRIORITY_LOW    (NORMAL)   → 15 minutes (4 packets/hour)
  • PRIORITY_MEDIUM (ABNORMAL) → 5 minutes
  • PRIORITY_HIGH   (CRITICAL) → 1 minute + IMMEDIATE DISPATCH

  Store-and-Forward Retry Queue:
  • FIFO queue, max 12 packets
  • HIGH priority → front of queue
  • LOW priority → back of queue
  • Retry every 30 seconds
  • Oldest evicted when full

  HQ GATEWAY FIRMWARE:
  • Continuous LoRa receive mode (parsePacket)
  • CRC32 validation BEFORE decryption
  • AES-CTR decryption with nonce
  • Binary vs text format detection
  • HMAC-SHA256 HTTP forwarding
  • In-memory HTTP retry queue (30s interval)
  • Relay control polling (every 4 seconds)

  SLIDE 10 — SOFTWARE IMPLEMENTATION: LORA COMMUNICATION

Title:
  Software Implementation — LoRa Communication Protocol

Content:

  PACKET STRUCTURE:

  ┌──────────┬──────────┬──────────────────┬────────┐
  │ HEADER   │ NONCE    │ ENCRYPTED        │ CRC32  │
  │ 23 bytes │ 16 bytes │ PAYLOAD          │ 4 bytes│
  │          │          │ (variable)       │        │
  ├──────────┴──────────┴──────────────────┴────────┤
  │◄─────── Encrypted Payload Region ───────────────►│
  └──────────────────────────────────────────────────┘

  HEADER (23 bytes):
  ┌────────┬──────┬──────────────────────────────────┐
  │ Offset │ Size │ Field           │ Description     │
  ├────────┼──────┼─────────────────┼─────────────────┤
  │ 0      │ 4    │ magic           │ 0x31504653      │
  │ 4      │ 1    │ version         │ 0x01            │
  │ 5      │ 16   │ hardwareId      │ EUI-64 hex      │
  │ 21     │ 2    │ payloadLength   │ LE uint16       │
  └────────┴──────┴─────────────────┴─────────────────┘

  BINARY PAYLOAD ENCODING:
  [num_readings:1B] [pin:1B] [type:1B] [value:2B] ...

  • Each reading = 4 bytes (fixed offset for simple parsing)
  • Value = int16_t scaled by 10 (25.3 → 253)
  • Special sentinels: 0x7FFF = NaN, 0x7FFE = Error
  • Max 24 readings per packet (< 96 bytes payload)
  • ~70% size reduction vs text format (~30 bytes vs ~100 bytes for 7 readings)

  ENCRYPTION — AES-128-CTR:
  • Why CTR mode: no padding, no padding oracle attacks
  • Unique 16-byte nonce per packet (esp_random + millis)
  • Semantic security: same plaintext → different ciphertext
  • Hardware-accelerated via mbedTLS on ESP32

  CHANNEL ACTIVITY DETECTION (CAD):
  1. Sample RSSI in receive mode
  2. If RSSI < -95 dBm → channel clear → transmit
  3. If RSSI >= -95 dBm → wait 20-100ms random → retry
  4. After 5 failed attempts → transmit anyway (fail-open)

  ADAPTIVE DATA RATE (ADR):
  ┌──────────────────┬──────────────────┬──────────────────┐
  │ RSSI Condition   │ Spreading Factor │ Air Time (50B)  │
  ├──────────────────┼──────────────────┼──────────────────┤
  │ RSSI > -100 dBm  │ SF7              │ ~30 ms           │
  │ -110 to -100     │ SF8              │ ~55 ms           │
  │ -120 to -110     │ SF9              │ ~100 ms          │
  │ RSSI <= -120     │ SF10             │ ~185 ms          │
  └──────────────────┴──────────────────┴──────────────────┘
  • Updated every 60 seconds based on best RSSI from HQ ACK
  • SF7 = ~85% less airtime than SF10

--------------------------------------------------------------------------------
  Notes for presenter:
  - Explain why binary encoding matters for LoRa (limited bandwidth)
  - The AES-CTR + nonce system ensures security without per-packet overhead
  - CAD prevents collisions, ADR optimizes power/bandwidth

  SLIDE 14 — SOFTWARE IMPLEMENTATION: NFC CONFIGURATION
================================================================================

Title:
  Software Implementation — NFC Configuration System

Content:

  PURPOSE:
  • Replace WiFi AP configuration with tap-to-config workflow
  • Essential for 38-pin node variant (no WiFi AP)
  • Enables field reconfiguration without opening enclosure

  TWO COMPLEMENTARY PATHS:

  Path A — Android HCE (Direct Phone Tap):
  ┌──────────────────────────────────────────────────────────────┐
  │ [Android Phone] ──ISO-DEP APDU── [PN532] ──I2C── [ESP32]    │
  │                                                               │
  │ Protocol:                                                     │
  │ 1. SELECT AID: 00 A4 04 00 0B F0 53 4D 41 52 54 50 4F 4E   │
  │                 49 43 00                                      │
  │    → Response: 90 00 (success)                               │
  │ 2. GET LENGTH: 00 CA 00 00 04                                │
  │    → Response: [4-byte payload length] + 90 00               │
  │ 3. READ BINARY: 00 B0 [offset_hi] [offset_lo] [max_len]     │
  │    → Response: [data chunk] + 90 00                          │
  │                                                               │
  • AID: F0.53.4D.41.52.54.50.4F.4E.49.43 ("SMARTPONIC")        │
  • Payload: [16-byte IV] + [AES-CTR encrypted JSON config]       │
  • Max payload: 512 bytes                                        │
  • Read in 48-byte chunks                                        │
  └──────────────────────────────────────────────────────────────┘

  Path B — NTAG215 Physical Tag (iOS Fallback):
  ┌──────────────────────────────────────────────────────────────┐
  │ [Phone] ──NFC write── [NTAG215 Tag] ──NFC read── [ESP32]    │
  │                                                               │
  • NTAG215: 135 pages × 4 bytes = 540 bytes total               │
  • Pages 4-135: user memory (504 bytes usable)                   │
  • NDEF format: [Header][Type Len][Payload Len][Type][Payload]  │
  • Encrypted payload extracted from NDEF record                  │
  • iOS limitation: no third-party HCE → physical tag required   │
  └──────────────────────────────────────────────────────────────┘

  IMPLEMENTATION DETAILS:
  • Non-blocking background polling (3s interval in STATE_CONNECTED)
  • PN532 init at end of setup() — no boot delay
  • HCE attempted first; NTAG215 as automatic fallback
  • AES-128-CTR decryption (same key as LoRa)
  • Live config application via applyNfcSensorConfig() — no reboot
  • LED indicator (GPIO2): solid while waiting, flash on success

  SECURITY:
  • Same AES-128-CTR encryption as LoRa layer
  • Sequence number in JSON prevents replay attacks
  • Physical access required for NFC configuration
  • Optional node_key header for additional protection

  Notes for presenter:
  - NFC is a convenience feature — makes field configuration practical
  - The dual-path approach (HCE + tag) covers both Android and iOS
  - Non-blocking design means NFC doesn't delay normal operation

  EXECUTION MODES:

  AUTO (Automatic):
  ┌──────────────────────────────────────────────────────────────┐
  │ Threshold crossed → create relay_command (status=pending)    │
  │ → send Telegram notification → HQ polls → forwards to node    │
  │                                                               │
  │ Used for: Safe, reversible actions (water circulation)       │
  └──────────────────────────────────────────────────────────────┘

  ┌──────────────────────────────────────────────────────────────┐
  │ Threshold crossed → create pending_approval                  │
  │ → send Telegram approval request → wait for /approve or      │
  │   /cancel → on approve: execute → on cancel: discard        │
  │                                                               │
  │ 10-minute expiration on pending approvals                     │
  │ Used for: Chemistry-affecting actions (pH adjustment)         │
  └──────────────────────────────────────────────────────────────┘

  ┌──────────────────────────────────────────────────────────────┐
  │ Threshold crossed → send Telegram alert only                  │
  │ No relay action taken                                         │
  │                                                               │
  │ Used for: Actions requiring human judgment (heating, HVAC)   │
  └──────────────────────────────────────────────────────────────┘

  SAFETY PRINCIPLES:
  1. AUTO only for physically safe, reversible actions
  2. APPROVAL_REQUIRED for chemistry-affecting actions
  3. ALERT_ONLY for ambiguous situations
  4. Independent cooldowns per rule (prevents flapping)
  5. 10-minute expiration on pending approvals
  6. Chat ID verification on /approve and /cancel
  7. Hardware interlock: physical relay override always possible

  SLIDE 18 — SECURITY ARCHITECTURE
================================================================================

Title:
  Security Architecture — Defense in Depth

Content:

  LAYER 1 — LoRa Wireless (AES-128-CTR + CRC32):
  ┌──────────────────────────────────────────────────────────────┐
  │ • All payloads encrypted with AES-128-CTR                    │
  │ • Unique 16-byte nonce per packet (semantic security)        │
  │ • CRC32 validated BEFORE decryption (reject early)           │
  │ • No padding → no padding oracle attacks                     │
  │ • Hardware-accelerated via mbedTLS on ESP32                  │
  └──────────────────────────────────────────────────────────────┘

  LAYER 2 — HTTP API (HMAC-SHA256):
  ┌──────────────────────────────────────────────────────────────┐
  │ • X-API-Key: authenticates the caller (HQ only)              │
  │ • X-Timestamp: 5-minute window prevents replay attacks      │
  │ • X-Signature: HMAC-SHA256 ensures body integrity           │
  │ • Constant-time comparison (hash_equals) prevents timing    │
  │   side-channel attacks                                       │
  └──────────────────────────────────────────────────────────────┘

  LAYER 3 — Node Configuration (X-Node-Key):
  ┌──────────────────────────────────────────────────────────────┐
  │ • Bootstrap mode: no key configured → allow deployment        │
  │ • Protected mode: key configured → require matching header   │
  │ • Invalid key → HTTP 403 Forbidden                           │
  │ • Prevents unauthorized reconfiguration after deployment     │
  └──────────────────────────────────────────────────────────────┘

  LAYER 4 — Telegram Access Control (Chat-ID Allowlist):
  ┌──────────────────────────────────────────────────────────────┐
  │ • Only pre-authorized chat IDs can interact with the bot     │
  │ • /whoami command helps users discover their chat ID         │
  │ • Unauthorized requests silently rejected                    │
  │ • All commands validated against allowlist                   │
  └──────────────────────────────────────────────────────────────┘

  LAYER 5 — NFC Configuration (AES-CTR + Sequence Number):
  ┌──────────────────────────────────────────────────────────────┐
  │ • Same AES-128-CTR encryption as LoRa layer                  │
  │ • Sequence number in JSON prevents replay attacks            │
  │ • Physical access required for NFC tap                       │
  │ • Optional NTAG215 password protection                       │
  └──────────────────────────────────────────────────────────────┘

  SECURITY SUMMARY:
  ┌──────────────────────────────────────────────────────────────┐
  │ Attack Vector          │ Protection                          │
  ├────────────────────────┼────────────────────────────────────┤
  │ LoRa eavesdropping     │ AES-128-CTR encryption              │
  │ LoRa replay            │ Unique nonce per packet             │
  │ LoRa bit-flip          │ CRC32 integrity check               │
  │ HTTP replay            │ 5-minute timestamp window           │
  │ HTTP tampering         │ HMAC-SHA256 signature               │
  │ Unauthorized API calls │ X-API-Key authentication            │
  │ Unauthorized Telegram  │ Chat-ID allowlist                   │
  │ NFC replay             │ Sequence number in payload          │
  │ Node reconfiguration   │ X-Node-Key protection               │
  └──────────────────────────────────────────────────────────────┘

  FUTURE SECURITY ENHANCEMENTS:
  • Replace hardcoded AES key with ESP32 secure boot / eFuse
  • HTTPS/TLS for PHP API endpoints
  • OAuth2 for dashboard authentication

--------------------------------------------------------------------------------
  Notes for presenter:
  - Defense in depth: multiple independent security layers
  - Each layer protects a different attack vector
  - The 5-minute timestamp + HMAC is a proven pattern for IoT APIs

     • Full round-trip control: Telegram → PHP → HQ → LoRa → Node
     • Relay command acknowledgment pipeline
     • Real-time status queries

  4. DATA RELIABILITY
     • Node-side FIFO retry queue (max 12 packets)
     • HQ-side HTTP retry queue
     • Store-and-forward architecture

  5. OPERATIONAL ALERTING
     • Threshold-based alerts with cooldown deduplication
     • Freshness monitoring (STALE / OFFLINE / RECOVERED)
     • Multi-channel: Telegram + Web Dashboard

  6. PREDICTIVE ANALYTICS
     • Trend projection with breach detection
     • What-If simulation
     • Health prediction with anomaly scoring

  7. NFC CONFIGURATION
     • Android HCE direct phone tap
     • NTAG215 physical tag fallback (iOS)
     • Non-blocking background polling

  8. EVENT-DRIVEN AUTOMATION
     • Three-tier safety model (AUTO / APPROVAL / ALERT_ONLY)
     • Human-in-the-loop for unsafe actions
     • Independent cooldowns per rule
