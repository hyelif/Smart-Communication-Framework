HCE APDU Protocol (must match ESP32 side)
------------------------------------------
Phone (HCE) must respond to these commands from PN532:
1. SELECT AID: 00 A4 04 00 0B F0 53 4D 41 52 54 50 4F 4E 49 43 00
   → Success: 90 00
2. GET LENGTH: 00 CA 00 00 04
   → Response: [4-byte payload length] + 90 00
3. READ: 00 B0 [offset_hi] [offset_lo] [max_len]
   → Response: [data chunk] + 90 00
- Payload: [16-byte IV] + [AES-CTR encrypted JSON config]
- Max payload: 512 bytes (IV + ~496 bytes ciphertext)

- Sequence number to prevent replay attacks
- Security key verification (same as WiFi AP /config endpoint)
- Optional: NTAG password protection (32-bit password stored in ESP32)

Payload Structure (CBOR encoded, then AES encrypted)
----------------------------------------------------
{
  "config": [...],           // Same as WiFi AP config array
  "nodeId": 1,
  "latitude": 3.123456,
  "longitude": 101.123456,
  "distance": 10.5,
  "calibration": {...},      // Calibration profiles
  "keys": {...},             // Optional: AES/Auth keys
  "seq": 12345,              // Sequence number (anti-replay)
  "ts": 1714377600           // Timestamp (Unix epoch)
}

================================================================================
                    Progress Update - 38-Pin Node Variant
================================================================================
Date: 2026-05-01

Goal
- Support larger ESP32 38-pin node deployments without exceeding the 255-byte LoRa packet limit
- Keep hardware_id as the real identity for multi-node differentiation
- Avoid changing HQ/PHP sensor parsing format

Design Decision
---------------
Chosen option: split telemetry into multiple LoRa packets.

Reason:
- LoRa library packet limit is 255 bytes.
- SmartPacket overhead is 34 bytes, leaving about 221 bytes for encrypted plaintext.
- Keeping readable text segments preserves current HQ parsing and PHP storage behavior.
- Compact binary sensor IDs would save bytes but requires a larger HQ/PHP/dashboard mapping refactor.

New Firmware Variant
--------------------
Path:
- firmware_esp32/ESP32_Node_38Pin

Behavior:
- Based on ESP32_Node WiFi AP configuration firmware
- Uses hardware_id only in encrypted payload metadata
- Removes node= from encrypted telemetry/location/ACK payloads
- Increases MAX_SENSORS to 24
- Expands allowed GPIO list for 38-pin ESP32 while avoiding LoRa SPI pins
- Splits telemetry into packet chunks using packet_part metadata
- Each chunk gets its own sequence number, nonce, AES-CTR encryption, CRC32, and LoRa packet

Backend / HQ Compatibility
--------------------------
- HQ accepts packets that contain hardware_id even when node= is absent
- HQ ignores packet_part as metadata
- PHP accepts hardware_id as identity and resolves/creates the backend nodes.id internally
- Existing database still uses node_id as an internal relational key, but operator-facing identity is hardware_id
