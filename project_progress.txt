                     LORA OPTIMIZATION (COMPLETED 2026-05-28)
================================================================================

Four optimizations implemented to improve LoRa throughput, reliability, and
power efficiency on the ESP32 Node 38-Pin firmware, with matching changes on
the ESP32 HQ Site receiver.

1. BINARY PAYLOAD ENCODING
   [DONE] SmartPacket.h: Added SensorType enum, binary format constants
         (BIN_VALUE_NAN, BIN_VALUE_ERROR, BIN_READING_SIZE, etc.), helper
         functions (sensorNameToType, sensorTypeToName, isBinaryFormat)
   [DONE] SmartPacket.h: Binary payload format defined as:
         [num_readings:1B] [pin:1B] [type:1B] [value:2B] ...
         value is int16_t scaled by 10 (25.3 -> 253)
         Special values: 0x7FFF=NaN, 0x7FFE=Error/Disconnected
   [DONE] PacketBuilder.h/cpp: Added build() overload accepting raw
         const uint8_t* binary data + length (encrypts directly without
         text conversion). Original String-based build() delegates to it.
   [DONE] main.cpp: buildBinaryPayload() replaces buildPayload() for
         telemetry. Converts SensorReading vector to compact binary.
         ~70% size reduction: ~30 bytes vs ~100 bytes for 7 readings.
   [DONE] LoRaReceiver.h/cpp: PacketResult gains binPayload vector +
         isBinaryFormat flag. decrypt() returns both String and raw
         vector. processPacket() detects format via isBinaryFormat()
         and stores accordingly.
   [DONE] HttpForwarder.cpp: buildTelemetryJson() parses binary format
         (count + pin/type/value triplets) into same JSON structure as
         before. Text fallback preserved for registration/legacy.
   [DONE] All 3 SmartPacket.h copies synced (top-level canonical,
         Node_38Pin/shared, HQ_Site/shared)

2. REMOVE AUTH KEY FROM TELEMETRY PACKETS
   [DONE] main.cpp: buildBinaryPayload() does NOT include auth key.
         Auth is only in registration packets (buildRegistrationPayload).
   [DONE] LoRaReceiver.cpp: Auth validation only applies to text
         packets. Binary telemetry skips auth check — hardware ID in
         the packet header is sufficient after registration.
   [DONE] Registration packets (cmd=hello) still carry auth=AQUA77 for
         initial handshake security.

3. CHANNEL ACTIVITY DETECTION (CAD)
   [DONE] main.cpp: isChannelClear() samples LoRa RSSI in RX mode.
         If RSSI > -95 dBm, channel is considered busy.
   [DONE] main.cpp: waitForClearChannel() retries up to 5 times with
         random 20-100ms backoff. Transmits anyway after timeout
         (fail-open to avoid starvation).
   [DONE] CAD called before both registration and telemetry TX.

4. ADAPTIVE DATA RATE (ADR)
   [DONE] SmartPacket.h: ADR RSSI thresholds defined (-100 for SF7,
         -110 for SF8, -120 for SF9, else SF10).
   [DONE] main.cpp: gBestHqRssi tracks best RSSI from HQ responses.
         checkLoRaResponse() captures LoRa.packetRssi() on every
         valid response.
   [DONE] main.cpp: updateAdr() adjusts Spreading Factor based on
         best RSSI. Runs every 60s (ADR_UPDATE_INTERVAL_MS).
   [DONE] Current SF displayed in telemetry log header.

Automation Rules (Confirmed)
---------------------------
| Sensor    | Condition         | Action          | Mode              | Why                       |
|-----------|-------------------|-----------------|-------------------|---------------------------|
| Turbidity | > 300 NTU        | Pump ON         | AUTO              | Safe - filtration cycle   |
| Turbidity | < 250 NTU        | Pump OFF        | AUTO              | Safe - cleanup done       |

Execution Modes
--------------
AUTO              : Executes relay action immediately + Telegram notification
APPROVAL_REQUIRED : Creates pending approval, sends Telegram request, waits for /approve
ALERT_ONLY        : Sends Telegram alert only, no relay action

Safety Principles
-----------------
1. AUTO mode only for physically safe, reversible actions (water circulation)
2. APPROVAL_REQUIRED for actions affecting chemistry (pH, nutrients)
3. ALERT_ONLY for sensor readings requiring human judgment
4. Each rule has independent cooldown to prevent flapping
5. 10-minute expiration on pending approvals prevents stale commands
6. Chat ID verification on approve/cancel prevents unauthorized control

| SCL       | GPIO 22 |
| IRQ       | Not connected (or GPIO 23 for interrupt) |

Workflow (Android - Direct Phone Tap)
-------------------------------------
1. User configures ESP32 settings in Flutter app
2. User taps "Deploy via NFC" button
3. Phone enters NFC card emulation mode (HCE)
4. User taps phone to ESP32's PN532 reader
5. ESP32 reads phone's emulated card, decrypts config
6. ESP32 stores to Preferences, sends ACK via NFC
7. Phone shows confirmation ("Config deployed!")

Workflow (iOS - NFC Tag)
------------------------
iOS does NOT support HCE for third-party apps.
1. User configures ESP32 in Flutter app
2. User taps phone to NTAG215 tag → writes encrypted config
3. User taps tag to ESP32's PN532 reader
4. ESP32 reads tag, decrypts, stores config

HCE APDU Protocol (must match ESP32 side)
------------------------------------------
Phone (HCE) must respond to these commands from PN532:
1. SELECT AID: 00 A4 04 00 0B F0 53 4D 41 52 54 50 4F 4E 49 43 00
   → Success: 90 00
2. GET LENGTH: 00 CA 00 00 04
   → Response: [4-byte payload length] + 90 00
3. READ: 00 B0 [offset_hi] [offset_lo] [max_len]
   → Response: [data chunk] + 90 00
- Payload: [16-byte IV] + [AES-CTR encrypted JSON config]
- Max payload: 512 bytes (IV + ~496 bytes ciphertext)

================================================================================
                     PACKET STRUCTURE
================================================================================

Binary packet: [HEADER:23][NONCE:16][ENCRYPTED_PAYLOAD][CRC32:4]

Header (23 bytes):
  - magic:        uint32_t (0x31504653 = "SPF1")
  - version:      uint8_t  (0x01)
  - hardwareId:   uint8_t[16] (16-char uppercase hex)
  - payloadLength: uint16_t (encrypted payload size, LE)

Max packet size: 255 bytes
Min packet size: 44 bytes

Date: 2026-05-26

Decision
---------
Supabase cloud database migration ABANDONED due to IPv6 limitation.
Supabase PostgreSQL only exposes AAAA (IPv6) DNS records, and the local
development environment lacks IPv6 connectivity. PHP/Laravel cannot resolve
or connect to the database host.

Lesson Learned
---------------
- Supabase database connections are IPv6-only (no IPv4 address)
- Local XAMPP/PHP on this network cannot resolve AAAA records
- Cloud database migration requires IPv6-capable infrastructure
- Future cloud consideration: use a database provider with IPv4 support
  (e.g., DigitalOcean Managed DB, AWS RDS, or a VPS with PostgreSQL)
