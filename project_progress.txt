SmartPonic Project Progress Update
Date: 2026-04-23

Completed Work

1. Smart Communication Framework - FULLY IMPLEMENTED
   [OK] Adaptive Communication Strategy
     - 5-second sensor sampling interval
     - Dynamic reporting intervals: NORMAL (15min), ABNORMAL (5min), CRITICAL (1min)
     - CRITICAL condition bypasses interval, sends immediately
   [OK] Data Prioritization
     - Priority levels: LOW, MEDIUM, HIGH
     - HIGH priority packets bypass queue, sent immediately
     - Payload includes priority flag and report mode
   [OK] Store-and-Forward Reliability
     - Node: FIFO retry buffer (12 packets max)
     - HQ: SD/SPIFFS backed HTTP retry queue
     - 30-second retry intervals
   [OK] Security Implementation (AES-CTR)
     - Stage 1: Removed HEX encoding, raw binary transmission
     - Stage 2: Structured packet [HEADER|NONCE|PAYLOAD|CHECKSUM]
     - Stage 3: CRC32 validation BEFORE decryption (validate -> decrypt)
     - Stage 4: AES-CTR mode encryption with 16-byte nonce

2. Packet Structure
   +------------------+-------------------+--------------------+------------------+
   | HEADER (14 bytes)| NONCE (16 bytes)  | ENCRYPTED PAYLOAD  | CRC32 (4 bytes)  |
   +------------------+-------------------+--------------------+------------------+
   Header contains: magic, version, nodeId, priority, reportMode, payloadLength, sequence

3. Communication Analytics
   - Dashboard captures: critical_event_count, priority_percentages
   - Min/Max/Avg sensor stats per time range
   - Signal quality tracking (RSSI/SNR)

4. Database Schema (init.sql)
   - sensor_readings: priority_level, report_mode, sequence_number, latitude, longitude, distance_m
   - Dedicated per-sensor tables: temperature_data, humidity_data, water_temp_data, ph_data, tds_data, turbidity_data, rain_data
   - invalid_sensor_data: tracks sensor errors with reason

5. HQ Gateway Capabilities
   - Binary LoRa packet reception
   - CRC32 integrity validation before decryption
   - AES-CTR decryption with nonce-based IV
   - Structured packet parsing (nodeId, priority, reportMode, sequence)
   - RSSI/SNR capture for signal quality monitoring
   - Location metadata (lat/lon/distance) extraction
   - HMAC-SHA256 signed HTTP requests to PHP API
   - SD-first offline storage (no SPIFFS fallback by default)
     - Logs every received packet to SD (NDJSON)
     - Uses SD-backed HTTP retry queue when Wi-Fi/PHP is down

6. Node Capabilities
   - Dynamic GPIO sensor configuration (max 15 sensors)
   - Priority escalation based on readings (nan, out-of-range detection)
   - Location metadata sync via separate packet type
   - No retry queue for failed LoRa transmissions (drops on failure; HQ handles persistence)
   - Serial command interface for config management
   - Calibration profiles supported (threshold_min/max + calibration_a/b/c)
     - Receives profiles from Flutter deploy payload (calibration block)
     - Applies calibration coefficients to live sensor readings
     - Uses profile thresholds for MEDIUM/HIGH priority classification

7. PHP Backend (receive_data.php)
   - Validates: API key, timestamp, HMAC signature
   - Stores: priority_level, report_mode, sequence_number, lat/lon/distance, RSSI
   - Routes sensors to dedicated tables
   - Tracks invalid sensor readings with reason

8. Dashboard Features
   - Communication Overview panel with priority/report mode/sequence
   - Location metadata display (coordinates, distance)
   - Communication analytics (critical events, priority percentages)
   - Signal trace in Activity tab
   - Health monitoring with freshness detection
   - Threshold-based alerts

9. Security Baseline
   [OK] LoRa payload: AES-128-CTR encryption
   [OK] Integrity: CRC32 checksum (validated before decrypt)
   [OK] HQ->PHP: X-API-Key + X-Timestamp + X-Signature (HMAC-SHA256)
   [OK] Node config: X-Node-Key protection
   [OK] Request timestamp validation (replay protection)
   [OK] Strict input validation (node_id, sensor count, pin format, sensor name)
